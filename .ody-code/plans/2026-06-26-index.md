# Phase A1 CLI 启动约定统一 Implementation Plan

**Goal:** 在 Rust `ody-host` 中新增 `serve` 子命令并复用现有全局 flags，同时在 TS SDK 的 `createExternalTransport` 中增加 spawn error 监听，最终形成可执行的跨语言 CLI 合同。

**Architecture:** Rust 侧通过 clap 子命令与全局 flags 共存（互斥）的方式，让 `ody-host serve --stdio` 与 `ody-host --stdio` 产生相同的 `HostConfig`；TS 侧保持向外部 binary 传递 `serve` 参数，并封装带 `proc.once('error')` 监听的 `spawnHost` 辅助函数，使启动失败以明确错误消息立即 reject。

**Tech Stack:** Rust (clap 4, cargo test), TypeScript/Vitest (packages/node-sdk), Markdown ADR.

> For executing workers: implement this plan task-by-task (prefer a fresh subagent/Task per task — a clean context per task avoids single-session degradation). Steps use - [ ] checkboxes for tracking.

## Risks & Open Questions

| # | Risk | Mitigation |
|---|---|---|
| R1 | clap 4 的 `args_conflicts_with_subcommands` 与 `#[command(flatten)]` 配合行为不确定 | 采用手动互斥检测 fallback；Task 1 的测试必须覆盖 `ody-host --stdio serve --socket-path /x.sock` 拒绝场景 |
| R2 | `proc.once('error')` 与 `waitForReadyMessage` 的 resolve/reject 竞态导致重复 reject 或内存泄漏 | Task 4 引入单次 `settled` 标志与 `cleanup()`，单元测试模拟 `ENOENT` 与成功 ready 同时到达场景 |
| R3 | `waitForReadyMessage` 内部不处理 stderr close/timeout，spawn error 是其唯一快速失败路径 | Task 4 的错误消息必须包含 `binaryPath` 与完整 `argv`，方便调用方定位 |
| R4 | mock test 对 `serve` 的断言与未来 TS `ody serve` 子命令重构冲突 | Task 5 只断言 `process.argv[2] === 'serve'`，不检查 flag 名称 |
