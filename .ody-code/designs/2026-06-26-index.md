## Architecture

```
TS 客户端路径:
SDKRpcClient.connect(options)
  └─ createExternalTransport(options, dispatch)
       ├─ spawn(binaryPath, ['serve', '--stdio', ...extraArgs])  [C:USER]
       ├─ proc.on('error') -> reject with binaryPath + args      [C:USER]
       └─ waitForReadyMessage(proc.stderr, predicate)
            └─ createStreamTransport(...) -> ExternalTransportResult

Rust 服务端路径:
ody-host serve --stdio
  └─ HostConfig::from_cli(std::env::args())
       ├─ clap 解析: 接受全局 flags 或 serve subcommand + 相同 flags [C:USER]
       ├─ 统一构造 HostConfig { transport, home_dir, config_path, ... }
       └─ main() -> CoreHost::new -> build_transport -> serve
```

数据变化点：
- `std::env::args()` 中的字符串 `serve` 在 `HostConfig::from_cli` 内被 clap 消费，输出结构化的 `HostConfig`。
- TS spawn 的 argv 中仍包含 `serve`，Rust 解析后行为与旧全局 flags 一致。

## Algorithms

### Rust 侧：解析全局 flags 或 `serve` 子命令

```
function HostConfig::from_cli(args):
    cli = Cli::parse_from(args)
    active = choose_active_args(cli)          // 全局 flags 或 Command::Serve 的 ServeArgs
    home_dir = active.home.unwrap_or(default_home_dir())
    config_path = active.config.or_else(lookup_default_config(home_dir))
    file = load_raw_config(config_path) if exists else empty
    transport = build_transport(active)       // socket_path > tcp > stdio
    log_level = parse_log_level(active.log_level)
    provider = build_provider(file)
    return HostConfig { home_dir, config_path, transport, log_level, provider }
```

### TS 侧：带 error 监听的 spawn

```
function spawnHost(binaryPath, argv, transportPredicate):
    proc = spawn(binaryPath, argv, { stdio: ['pipe', 'pipe', 'pipe'] })
    return new Promise((resolve, reject) => {
        onError = (err) => {
            cleanup()
            reject(new Error(`Failed to spawn host ${binaryPath} with args ${JSON.stringify(argv)}: ${err.message}`))
        }
        proc.once('error', onError)
        waitForReadyMessage(proc.stderr, transportPredicate)
            .then((msg) => { cleanup(); resolve({ proc, readyMessage: msg }) })
            .catch((err) => { cleanup(); reject(err) })
    })
```

## Error Handling

| Error Class | Immediate Handling | Degradation Path | Recovery Condition |
|---|---|---|---|
| clap 解析失败（未知 flag / 缺少 value） | clap 自动打印 usage 并 exit code ≠ 0 | 用户修正命令行 | 使用合法 argv 重新启动 |
| 全局 flags 与 `serve` flags 同时提供 | clap 拒绝（`error: unexpected argument`） | 用户去掉重复/冲突 flags | 只使用一种风格 |
| `serve` subcommand 使用旧 TS flag 名（如 `--socket`） | clap 报 `error: unexpected argument '--socket'` | 用户改用 `--socket-path` | 使用 Rust 全局 flag 名 |
| TS `spawn` 失败（ENOENT / EACCES / EMFILE） | `spawnHost` reject，消息包含 binaryPath 和 argv | 调用方展示错误 | 修正 binary 路径或权限 |
| TS spawn 成功但 ready message 超时 | `waitForReadyMessage` 永不 resolve，调用方超时 | 调用方 `close()` 并报告启动超时 | 检查 host stderr 或 binary 版本 |

## Self-Review

### 高代价决策的输入/输出检查

#### D1 — Rust clap 全局 flags 与 `serve` subcommand 的解析

| # | 输入 argv | 期望输出 |
|---|---|---|
| 1 | `ody-host --stdio` | `HostConfig.transport == Stdio`（全局 flags 兼容） |
| 2 | `ody-host serve --stdio` | `HostConfig.transport == Stdio`（子命令路径） |
| 3 | `ody-host --stdio serve --socket-path /x.sock` | clap 报错（歧义/冲突，不静默合并） |

**验证状态**: 无法通过简单脚本验证 clap 行为，需在实现时通过 Rust 单元测试 T6 覆盖。若 clap 4 不支持目标行为，则回退到 A1b。

#### D2 — TS `createExternalTransport` spawn error 与 ready 超时的竞态

| # | 场景 | 期望行为 |
|---|---|---|
| 1 | `spawn` 立即 `ENOENT` | Promise reject，消息包含 binaryPath 和 argv |
| 2 | `spawn` 成功但 stderr 关闭无 ready | `waitForReadyMessage` 永不 resolve，调用方超时 |
| 3 | `spawn` 成功但 proc 10ms 后 emit error | 若 ready 已 resolve 则忽略；若未 resolve 则 reject |

**验证状态**: 通过 `node -e` 验证了 argv 构建（`serve` 始终在 argv[1]），但完整竞态测试需在 TS 单元测试中实现。

#### D3 — `serve` 参数位置

| # | 输入 | 期望 argv |
|---|---|---|
| 1 | `transport: 'stdio'` | `['serve', '--stdio']` |
| 2 | `transport: { socketPath: '/s', spawn: true }` | `['serve', '--socket-path', '/s']` |
| 3 | `transport: { host: 'h', port: 0, spawn: true }` | `['serve', '--tcp-host', 'h', '--tcp-port', '0']` |

**验证状态**: 已通过 `node -e` 验证，`serve` 始终位于索引 0，mock test 可安全断言 `process.argv[2] === 'serve'`。

### 四镜自查

- **Security**: 检查了所有 filter/regex。A1 未引入新 filter；secret（API key）仍通过配置文件读取，不在 CLI argv 中传递。未发现 PII 泄漏到日志或文件名的风险。
- **Test**: 每个新行为都有 must-pass 和 must-reject 用例：Rust 侧 `serve` 子命令的 T1-T6，TS 侧 spawn error 的 T3，mock `serve` 断言的 T1-T2。must-reject 用例包括未知 flag `--socket` 和不存在 binary。
- **Ops**: 新增 `proc.once('error')` 是单次事件监听，无显著延迟；clap 子命令解析在启动时一次性完成。无 identifier 冲突。并发场景不相关（每个 `SDKRpcClient.connect` 独立 spawn）。
- **Integration**: 验证了以下 hook 真实存在：
  - `HostConfig::from_cli` 在 `rust-ody/crates/ody-host/src/config.rs:74` [C:UPSTREAM]
  - `createExternalTransport` 在 `packages/node-sdk/src/rpc.ts:185` [C:UPSTREAM]
  - `waitForReadyMessage` 在 `packages/node-sdk/src/rpc.ts:277` [C:UPSTREAM]
  - `RustHostConnector` 通过 `SDKRpcClient.connect` 间接调用，不直接构造 argv [C:UPSTREAM]
  - clap 版本为 4（`rust-ody/Cargo.toml:12`）
- **Scope**: 本设计仍是一个连贯的 CLI contract 修复，未膨胀为独立子项目。Rust CLI 与 TS SDK 是同一合同的两面，因此保留在一个 split design 中。
